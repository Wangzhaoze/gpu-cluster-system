# 主机升级适配（2026-10-15）

目标硬件已经由Ubuntu和Docker确认：30个vCPU，61,678,247,936bytes内存（约57.44GiB），5张RTX5060Ti，各16311MiB显存。升级前审计见[容量审计](RESOURCE_AUDIT_2026-10-15.md)，其中旧资源数字为升级前快照。

本次适配：

- 将本机`.env`的`LOCAL_GPU_COUNT`从4调整到5，启动时补齐编号0–4的GPU槽位；监控已能看到5张卡。
- 通过Docker Engine读取CPU/RAM实际容量，API和Web输入均使用动态上限，避免继续提交32CPU/64GiB这类超主机资源的任务。
- `LAB_MEMORY_RESERVE_MB=8192`为Ubuntu、原生管理员编辑器及集群控制服务保留8GiB。工作区、训练和调试共享余下50,628MiB（49.4414GiB）；不是每个用户独享该容量。
- 全局调度计入所有STARTING/RUNNING任务和实际运行的成员工作区，不重复计算排队请求。CPU/内存不足时沿用FIFO等待；超过整机预算的旧排队配置明确失败，可由管理员调整后重新提交。既有运行任务不被强制缩容或停止。
- 工作区启停与调度共用已有数据库锁；没有资源时，在删除旧停止容器之前拒绝重建，保护现有工作区。
- 总览增加主机资源预算与已分配/可分配额度。额度是容器申请上限之和，不等同于实时RAM用量；运行在宿主机的外部程序仍会与集群竞争，系统预留不能防止任意外部程序耗尽内存。
- 保留学生账户、权限、每用户GPU上限、代码、环境、数据集、默认4CPU/4GB、调试8小时和单会话规则。5张卡由全体成员按配额共享，不自动把每个人的配额改成5。

三人并行可先规划每训练任务8CPU/12GB，同时三个工作区各2CPU/2GB，共30CPU、42GiB申请额度，加系统预留8GiB后仍留约7.44GiB余量。是否适合具体3D模型仍取决于输入体积、batch和缓存；资源不足的任务会排队，而非通过超配强行启动。
